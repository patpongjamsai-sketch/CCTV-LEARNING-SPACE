# LAB 2 — ห้องเรียน สมาชิก และความก้าวหน้า

เวลาโดยประมาณ: 120–150 นาที

## หลักการ

LAB นี้ต่อจาก LAB 1 และเพิ่มความสัมพันธ์ดังนี้:

```text
courses ──< classrooms ──< classroom_members >── profiles
   │              │                    │
   └──< units     └──< unit_progress >─┘
```

- `classrooms` คือห้องเรียนที่เปิดจากรายวิชา และมีครูเจ้าของหนึ่งคน
- `classroom_members` คือรายชื่อนักเรียน/ผู้ช่วยในแต่ละห้อง
- `unit_progress` คือความก้าวหน้าของสมาชิกแต่ละคนในแต่ละหน่วย
- Browser อ่านข้อมูลตาม RLS แต่ไม่มีสิทธิ์เขียนคะแนนหรือสถานะผ่าน
- Backend ต้องเป็นผู้ตรวจผลและบันทึกความก้าวหน้าใน LAB ถัดไป

## เป้าหมายการเรียนรู้

เมื่อจบ LAB นักเรียนจะสามารถ:

1. อธิบาย Foreign Key แบบคอลัมน์เดียวและแบบหลายคอลัมน์ได้
2. อธิบายเหตุผลที่ Progress ต้องอ้างถึงสมาชิก ห้อง และหน่วยเรียนได้
3. ทดสอบ Constraint ที่ป้องกันคะแนนหรือสถานะไม่สมเหตุผลได้
4. อธิบายความแตกต่างระหว่าง GRANT กับ RLS ได้
5. ตรวจสอบว่านักเรียนเห็นเฉพาะข้อมูลของตน และครูเห็นข้อมูลในห้องของตนได้

## ไฟล์และลำดับการทำงาน

1. `00_red_test.sql` — ทดสอบก่อนสร้าง ต้องขึ้นข้อความ `LAB 2 RED`
2. `01_create_schema.sql` — สร้าง Schema, Constraint, Index และ RLS
3. `02_seed_template.sql` — เพิ่มข้อมูลทดลองหลังแทน UUID ของ Auth User
4. `03_verify_lab.sql` — ตรวจโครงสร้างและกฎความปลอดภัย
5. `04_cleanup_lab.sql` — ล้างเฉพาะวัตถุของ LAB 2

> ใช้ Supabase Development Project เท่านั้น และรันไฟล์ตามลำดับ

## Predict

ก่อนทดลอง ให้ตอบคำถามต่อไปนี้:

1. ถ้าเพิ่ม Progress ให้คนที่ไม่ได้เป็นสมาชิกห้อง จะเกิดอะไรขึ้น
2. ถ้าห้องเรียนใช้ Course A แต่ Progress อ้าง Unit ของ Course B จะเกิดอะไรขึ้น
3. นักเรียนควรแก้ `best_score` จาก Browser ได้หรือไม่ เพราะเหตุใด
4. ครูห้อง A ควรอ่านรายชื่อสมาชิกห้อง B ได้หรือไม่

## ขั้นตอนทดลอง

### ขั้นที่ 1 — RED

รัน `00_red_test.sql` ก่อนสร้าง LAB 2 ต้องพบข้อผิดพลาดที่มีข้อความ `LAB 2 RED` ซึ่งยืนยันว่าการทดสอบจับกรณีที่ตารางยังไม่มีได้จริง

### ขั้นที่ 2 — สร้าง Schema

รัน `01_create_schema.sql` หนึ่งครั้ง ต้องได้ผลลัพธ์:

```text
LAB 2 schema created successfully
```

จากนั้นรัน `00_red_test.sql` ซ้ำ ต้องได้:

```text
LAB 2 GREEN: required tables and RLS are ready
```

### ขั้นที่ 3 — เตรียมผู้ใช้ทดลอง

1. ไปที่ Authentication → Users
2. สร้างผู้ใช้ทดสอบ 2 คน: ครู 1 คน และนักเรียน 1 คน
3. คัดลอก UUID ของทั้งสองคน
4. เปิด `02_seed_template.sql`
5. แทน `<TEACHER_AUTH_UUID>` และ `<STUDENT_AUTH_UUID>` ก่อน Run

ห้ามใช้ UUID ที่สร้างเอง เพราะ `profiles.id` อ้างอิง `auth.users.id`

### ขั้นที่ 4 — ตรวจสอบ

รัน `03_verify_lab.sql` ทีละ Section และบันทึกภาพผลลัพธ์เป็นหลักฐาน:

- ตารางและคอลัมน์
- Foreign Key และ Check Constraint
- Index
- RLS และ Policy
- สิทธิ์ที่ Browser ได้รับ
- ข้อมูลห้อง สมาชิก และ Progress

## Observe และ Analyze

บันทึกสิ่งที่สังเกตพบ แล้วอธิบาย:

1. Constraint ใดป้องกันสมาชิกซ้ำในห้องเดียวกัน
2. Constraint ใดป้องกัน Unit ข้าม Course
3. เพราะเหตุใด `completed` ต้องมี `progress_percent = 100`
4. เพราะเหตุใดเราไม่ให้ `authenticated` ทำ INSERT/UPDATE Progress โดยตรง

## คำถามตรวจความเข้าใจ

1. Primary Key ของ `classroom_members` ประกอบด้วยคอลัมน์ใดบ้าง
2. ถ้าลบ Classroom ข้อมูล Member และ Progress ควรเป็นอย่างไร
3. RLS ทำงานแทน Foreign Key ได้หรือไม่ เพราะเหตุใด
4. หากต้องการให้ครูผู้ช่วยจัดการสมาชิก ต้องเพิ่มกฎที่จุดใด
5. เหตุใดระบบคะแนนจึงต้องให้ Backend เป็นผู้ตัดสิน
